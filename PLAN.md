# PLAN.md

## Phase 1: Phase 1: Shared enums (LeaveStatus, LeaveType, EmploymentStatus)

Create src/shared/types/index.ts with three string enums: LeaveStatus ('pending', 'approved', 'rejected', 'cancelled'), LeaveType ('annual', 'sick', 'emergency'), and EmploymentStatus ('active', 'inactive', 'terminated'). Export all three enums from the barrel. Include Jest unit tests in tests/unit/shared/types.test.ts verifying each enum has the correct members.

## Phase 2: Phase 2: Knex configuration and database migrations

Create knexfile.ts at project root exporting a Knex config for PostgreSQL using DATABASE_URL from environment. Create three migration files in a new migrations/ directory: (1) migrations/001_create_employees.ts — creates the employees table with columns: id (uuid PK), employee_number (varchar unique), first_name, last_name, email, manager_id (nullable uuid), department (nullable varchar), hire_date (date), termination_date (nullable date), employment_status (varchar), created_at, updated_at, deleted_at (nullable timestamp). (2) migrations/002_create_leave_policies.ts — creates leave_policies table: id (uuid PK), policy_name, leave_type (varchar), entitlement_days (integer), accrual_rate (nullable float), max_accumulation (nullable float), minimum_notice_days (nullable integer), requires_manager_approval (boolean), is_active (boolean), created_at, updated_at. (3) migrations/003_create_leave_requests.ts — creates leave_requests table: id (uuid PK), employee_id (uuid FK→employees), leave_type_id (uuid FK→leave_policies), start_date (date), end_date (date), reason (nullable text), status (varchar), approved_by (nullable uuid FK→employees), approved_at (nullable timestamp), rejection_reason (nullable text), created_at, updated_at. Include a Jest test in tests/unit/shared/knex-config.test.ts verifying the knexfile exports a valid config object. This phase depends on src/shared/types/index.ts from Phase 1 — read it before writing migration files that reference enum values.

## Phase 6: Phase 6: Leave service (business logic)

Create src/modules/leave/leave.service.interface.ts with ILeaveService interface declaring: applyLeave(dto: CreateLeaveRequestDto): Promise<LeaveRequest>, approveLeave(leaveId: string, approverId: string): Promise<LeaveRequest>, rejectLeave(leaveId: string, approverId: string, reason: string): Promise<LeaveRequest>, cancelLeave(leaveId: string, employeeId: string): Promise<LeaveRequest>, getEmployeeLeaves(employeeId: string): Promise<LeaveRequest[]>, getPendingApprovals(managerId: string): Promise<LeaveRequest[]>. Create src/modules/leave/leave.service.ts with class LeaveService implementing ILeaveService. Constructor injects LeaveRepository, EmployeeRepository, PolicyRepository. applyLeave validates: employee exists and is active, policy exists and is active, startDate before endDate, no overlapping approved leave, minimum notice met if policy requires it. approveLeave validates: leave exists and is pending, approver is the employee's manager. rejectLeave validates: leave exists and is pending, approver is the employee's manager, reason is non-empty. cancelLeave validates: leave exists and is pending, employeeId matches the request owner. Update src/modules/leave/index.ts to export ILeaveService and LeaveService. Include Jest unit tests in tests/unit/modules/leave/leave.service.test.ts mocking all three repositories. This phase depends on src/modules/leave/leave.model.ts and src/modules/leave/leave.repository.ts from Phase 5, src/modules/employee/employee.repository.ts from Phase 3, and src/modules/policy/policy.repository.ts from Phase 4 — read these files before generating any code.

## Phase 7: Phase 7: Leave controller and routes

Create src/modules/leave/leave.controller.ts with class LeaveController. Constructor injects ILeaveService. Methods: applyLeave, approveLeave, rejectLeave, cancelLeave, getEmployeeLeaves, getPendingApprovals — each wraps the corresponding service call and returns a Fastify-compatible reply. Create src/modules/leave/leave.routes.ts exporting an async function leaveRoutes(fastify: FastifyInstance) that registers the following routes: POST /leaves (applyLeave), PATCH /leaves/:id/approve (approveLeave), PATCH /leaves/:id/reject (rejectLeave), PATCH /leaves/:id/cancel (cancelLeave), GET /leaves/employee/:employeeId (getEmployeeLeaves), GET /leaves/pending/:managerId (getPendingApprovals). Each route handler instantiates LeaveController with its dependencies (LeaveService with LeaveRepository, EmployeeRepository, PolicyRepository). Update src/modules/leave/index.ts to export LeaveController and leaveRoutes. Include Jest integration tests in tests/unit/modules/leave/leave.routes.test.ts using Fastify's inject method. This phase depends on src/modules/leave/leave.service.ts and src/modules/leave/leave.service.interface.ts from Phase 6, src/modules/leave/leave.repository.ts from Phase 5, src/modules/employee/employee.repository.ts from Phase 3, and src/modules/policy/policy.repository.ts from Phase 4 — read these files before generating any code.

## Phase 10: Phase 10: Balance migration and balance-aware leave service integration

Create migrations/004_create_leave_balances.ts — creates leave_balances table: id (uuid PK), employee_id (uuid FK→employees), leave_type_id (uuid FK→leave_policies), policy_id (uuid FK→leave_policies), entitlement_days (integer), used_days (integer default 0), pending_days (integer default 0), year (integer), created_at, updated_at, with a unique constraint on (employee_id, leave_type_id, year).

## Phase 1: Phase 1 — Migration: notifications.related_entity_code + leave_requests status/approver_id indexes

Create ONE new knex migration (PostgreSQL) — approximately 1 file, e.g. `migrations/20260915000000_add_related_entity_code_to_notifications.js`. Read `migrations/20260913000001_add_password_hash_to_employees.js` and `migrations/20260914000000_add_reverses_request_id_to_leave_requests.js` first and follow their exact file/export conventions (`exports.up` / `exports.down`, `knex.schema`), and read `migrations/20260913000000_initial_schema.js` to confirm the current `notifications` shape (it already creates `related_entity_type` and `related_entity_id` and a `(recipient_id, status)` index, but NO `(related_entity_type, related_entity_id)` index).

`exports.up` must do exactly two things:
1. `knex.schema.alterTable('notifications', (t) => { t.string('related_entity_code'); })` — NULLABLE, no default, no backfill, no NOT NULL. This is a GENERIC column (not leave-specific): it carries the related entity's human/machine code, and for this feature the leave type code. One migration, no new table.
2. Add the `(related_entity_type, related_entity_id)` index on `notifications` in THIS migration, alongside the column — `docs/ARCHITECTURE.md` already claims this index exists and this is the first feature whose entity linkage on notifications is load-bearing. Do NOT audit or restructure the rest of the initial migration; fix only this drift.

`exports.down` drops the index first, then the column.

Do NOT touch `leave_requests` DDL in this migration: the existing `(employee_id, status)` index already serves the pending-decisions predicate and `approver_id` needs no index for this query. No source files, no repository changes, no tests in this phase.

## Phase 3: Phase 3 — LeaveService.cancel: notify the approver inside the existing unit of work

ONE file: `src/modules/leave/leave.service.ts` (approximately 1 file). Read it in full first, plus `src/modules/leave/leave.model.ts` and `src/modules/notification/notification.model.ts` from Phase 2 — the `Notification.relatedEntityCode` field and the `CreateNotificationInput` shape are fixed contracts from that phase; do not re-declare or rename them.

Extend `LeaveService.cancel` so the approver notification ACCOMPANIES the requester's, inside the SAME existing `uow.withTransaction` callback, with the same `client` threaded through. Add a private `resolveApproverRecipient(request: LeaveRequest): Promise<string | null>` and call it once per cancellation, BEFORE the transaction (it reads the employee, not the transaction).

Binding rules to implement exactly:
1. The notification set is a function of the STATE CHANGE, not of who performed it. For a SUBMITTED or APPROVED cancellation there are exactly TWO `notificationService.create` calls — one to the requester (existing, unchanged) and one to the approver. For a DRAFT cancellation there is exactly ONE (requester only) — DRAFT notifies nobody else, matching the rule that a DRAFT cancellation touches no balance. Do NOT add a recipient list to the notifications table.
2. Recipient resolution: for an APPROVED cancellation the recipient is the ORIGINAL row's `request.approverId`. For a SUBMITTED cancellation it is the requester's direct manager — `(await this.employeeService.getEmployeeById(request.employeeId)).managerId`.
3. A missing recipient NEVER fails the cancellation. If the resolved recipient is `null` (a SUBMITTED request whose requester has `managerId === null`, or an APPROVED request whose `approverId` is null — a known, reachable legacy state), SKIP the approver notification and let the cancellation succeed (200). No transitive escalation, no ADMIN broadcast, no ConflictError, no assert-and-fail, no backfill. Record the skip in the CANCEL audit entry's metadata so the gap is visible rather than silent — the audit entry's SHAPE stays unchanged (same `action: AuditAction.CANCEL`, same `entityType: LEAVE_REQUEST_ENTITY_TYPE`, same `entityId` = the ORIGINAL request id, same `beforeState`/`afterState`); only the `afterState` payload may carry the skip marker.
4. Always notify, even when the cancelling actor IS the resolved recipient (the recorded approver cancelling their own approval, or a manager cancelling a direct report's SUBMITTED request). No self-authored marker, no suppression — this keeps "exactly two for SUBMITTED/APPROVED" unconditional and directly assertable.
5. GP-008 reversal path: YES, emit the approver notification. Read the recipient from the ORIGINAL row's `approverId` and key the notification's `relatedEntityId` to the ORIGINAL request id, NEVER the reversal row's id (the reversal row carries a null `approverId` by construction, so reading it there would silently drop every notification on that path).
6. The approver notification carries the request id and the leave type so the approver can act without a second lookup: `relatedEntityType: 'leave_request'`, `relatedEntityId` = the ORIGINAL request id, and `relatedEntityCode: request.leaveTypeCode` (the NEW nullable column from Phase 1/2 — this is the contract; the human-readable `message` may also mention the leave type, but the column is what matters). `type` stays the existing literal `'leave_request'` — no new discriminator. Title/message are composed inline in leave (e.g. title `'Leave request cancelled'`, message naming the request id and the leave type); no new shared type, no new DTO, no new module.
7. The existing requester notification and the existing CANCEL audit entry stay byte-identical in shape. Do NOT modify `LEAVE_REQUEST_ENTITY_TYPE`, the DRAFT/SUBMITTED in-place path, the APPROVED reversal path's balance release, the double-cancel guard, `assertCanCancel`, or the timing guard.

No route change (Phase 5), no `listPendingDecisions` (Phase 4), no tests in this phase (Phase 6).

## Phase 4: Phase 4 — LeaveService.listPendingDecisions

ONE file: `src/modules/leave/leave.service.ts` (approximately 1 file). Read it in full first, plus `src/modules/leave/leave.model.ts` and `src/modules/leave/leave.repository.ts` from Phase 2 — `PendingDecision` and `ILeaveRepository.findPendingDecisions` are fixed contracts from that phase; do not re-declare, rename, or re-implement them.

Add `listPendingDecisions(actor: LeaveActor): Promise<PendingDecision[]>` to `ILeaveService` and implement it on `LeaveService`. It takes NO query DTO and NO parameters beyond the actor.

Binding rules to implement exactly:
1. It is a queue of requests AWAITING A DECISION, not a decision history: SUBMITTED only. The repository's `status = 'SUBMITTED'` predicate owns that filter — do not add a second status filter in the service, and do not include APPROVED requests this approver decided.
2. Ordering is `start_date ASC` (oldest first, most urgent) and is owned by the repository's SQL — do NOT re-sort in the service.
3. Visibility follows the EXISTING role-scoped rule already used by `list`/`getById` in this same file: an ADMIN sees every SUBMITTED request (no `employeeIds` filter); a MANAGER sees their direct reports' — resolve them via `this.employeeService.getEmployeesByManagerId(actor.id)` and pass those ids as the scoping parameter. Do NOT re-express the rule differently from `list`; mirror its shape. Decide-scoping (excluding the caller's own request, or requests the caller may not decide) is DELIBERATELY DEFERRED to a follow-up — this endpoint must NOT grow a second copy of the decide rule, so do not call `assertCanDecide` and do not filter out the actor's own request.
4. Read-only: no `uow.withTransaction`, no `PoolClient` accepted or forwarded, no writes, no audit entry, no notification. Call `this.assertAuthenticated(actor)` first, exactly as `list`/`getById` do.
5. Return the repository's array verbatim — possibly empty (an empty queue is a valid 200, never an error), never `null`, no mapping, no cap, no pagination.

Do NOT add the route (Phase 5), do NOT modify `cancel` (Phase 3), and do NOT touch `src/modules/leave/leave.repository.ts`. No tests in this phase (Phase 6).
